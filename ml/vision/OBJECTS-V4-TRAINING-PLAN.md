# بصيرة — خطة استكمال تدريب الأشياء والأشكال V4 (مرحلة تجهيز البيانات، لا تدريب بعد)

**فرع الأساس:** `codex/basira-colour-quality-v3`، وهو فرع بحثي متراكم فوق V3 / معاينة iPhone وليس نسخة الإنتاج `main`. هذا العمل يحمي نسخة الكاميرا والتطبيق الأصلي وبيانات المستخدم. لا ننشر أوزانًا أو صورًا أو مفاتيح في GitHub.

## لماذا لا نُكرر تدريب V3؟

جميع أرقام V3 أدناه من **اختبار نهائي مستهلك** 136 صورة / 242 مرجعًا، وليست اختبارًا جديدًا. Tiny 86 TP / 61 FP / mAP 38.86% مقابل V3 86 TP / 62 FP / mAP 38.76%. الكراسي 0/6، الكتب 0/20، جميع الأجسام الصغيرة 0/49. السيارة ليست لها مراجع إيجابية كافية في نهائي V3، والشجرة ليست ضمن 80 فئة COCO. لا يصلح هذا النهائي لاختيار عتبات أو أوزان V4؛ الأرقام أعلاه لتحديد **مشكلة جمع البيانات فقط**.

الملف `ml/vision/objects-v4-targets.v1.json` يعرّف القائمة والتمييز بين مهام التدريب. يمكن لاحقًا إضافة فئات جديدة بشرط إصدار نسخة taxonomy جديدة ومراجع موثقة، لا تغيير أسماء الفئات بصمت.

## جمع البيانات المطلوب (ليس حالة منجزة)

ابدأ **بمسار واحد** مثل `chair + book` بدل محاولة تحسين 80 فئة دفعة واحدة. مطلوب صور حقيقية من مشاهد مستقلة وباختلاف الإضاءة والاتجاه والخلفية والحجم والحجب والمشهد الداخلي/الخارجي، مع صور سلبية **مراجعة صراحة** للفئات المستهدفة. عند جمع الفيديو يُثبت `captureGroupId` لكل جلسة/موقع/مجموعة مرتبطة حتى لا تتوزع إطارات المشهد نفسه بين التدريب والتحقق والنهائي.

بوابة الفحص البرمجية الحالية تفرض حدًا **أوليًا منخفضًا لفحص المجموعات**: 40 صورة تدريب و15 تحقق و20 نهائيًا، ومن مجموعتين مستقلتين على الأقل لكل قسم، و8 أمثلة تدريب و4 تحقق و4 نهائي لكل فئة مستهدفة من مجموعتين مختلفتين على الأقل. **تلك الحدود ليست حجم تدريب كافيًا ولا معيار جودة**. لزيادة فرصة اكتشاف تحسن حقيقي نوصي عمليًا بجمع مئات الأمثلة الجديدة للفئات التي فشلت، موزعة على مشاهد متعددة ومراجعين مستقلين؛ يحدد الحجم الفعلي بعد تحليل الأخطاء والتباين الإحصائي. صور فريق بصيرة الأصلية أو صور عامة مرخصة ومفحوصة الحقوق فقط، ولا نستخدم صور مستخدمي بصيرة تلقائيًا.

يجب أن تحتوي كل صورة على: ملف خاص موجود وبصمته SHA-256، دليل حقوق مستقل محفوظ، تصريح تدريب تجاري موثق لا يخلط بين رخصة الناشر وموافقة الأشخاص، فحص خصوصية (وجوه ولوحات وEXIF)، وسوم بشرية ومراجعة مستقلة، `verifiedExhaustiveClasses` لتفادي اعتبار الفئات غير الموسومة «لا توجد»، مربعات أو مضلعات مناسبة، ووسم شكل إذا كان ظاهرًا أو `uncertain`. **اقتراحات نموذج الكشف ليست ground truth**.

## منع تكرار مشكلات V2/V3

- رفض BDD100K ومشتقات أوزان V1/V2/المعلمين والـoptimizer وذاكرات الخصائص، وعدم إعادة تسمية مشتق مقيد للتظاهر بنظافته. البدء من وزن Tiny الرسمي الأصلي ذي بصمة SHA-256 المثبتة في policy.
- استبعاد الصور واللقطات ومجموعات المصدر من مجموعات الاختبار النهائي **السابقة والمستهلكة** عبر سجل شامل `protected-index.json` محلي موقع المراجعة. لا يحتوي المستودع على هذا السجل الخاص تلقائيًا، ولا يعوض وضع `coverageConfirmed=true` عن المراجعة البشرية.
- منع الصورة نفسها أو الجلسة نفسها في مجموعتين مختلفتين؛ يجب أيضًا إضافة فحص تشابه بصري وصلة المصدر/الموقع عند تجهيز مجموعة البيانات، لأن بصمة SHA وحدها لا تكشف الصور القريبة أو اقتصاص المشهد.
- حماية النهائي المستقل الجديد ومنع استخدامه لاختيار مرشح أو عتبة. لا يؤهل نجاح هذا المدقق وحده لتشغيل التدريب، ولا يثبت حقوق البيانات فعليًا بمجرد حقول JSON؛ يلزم فحص بشري مستقل للأصول وصحتها.
- لا تُرفع صور الأشخاص أو ملفات بيانات التدريب أو أرقام مفاتيح أو مواقع المستخدمين أو وسائط الالتقاط إلى GitHub أو صفحات المعاينة. اعتمد تخزينًا خاصًا مصرحًا به، ووثّق فترة الاحتفاظ والحذف.

## تشغيل فحص أهلية البيانات محليًا

أنشئ مجلدًا خاصًا **خارج المستودع** مثل `D:\\BasiraPrivate\\objects-v4\\` وضع فيه الملفات والحقوق والسجل الكامل للمجموعات النهائية التاريخية. ابدأ من القالبين `manifest.example.json` و`protected-index.example.json` لكن **لا تغيّر الموافقات إلى true قبل التدقيق الفعلي**. مثال من جذر المستودع:

```bash
node scripts/vision-object-finetune-v4/intake.mjs --manifest /PRIVATE/objects-v4/manifest.json --data-root /PRIVATE/objects-v4 --protected-index /PRIVATE/objects-v4/protected-index.json --report /PRIVATE/objects-v4/readiness.json
node --test scripts/vision-object-finetune-v4/intake.test.mjs
```

يُخرج المدقق أعدادًا مجمّعة، ولا يرفع صورًا أو إيميلات أو وسائط. فشله متوقع للقوالب الفارغة. اجتيازه يعني **فقط** أن تدقيقًا شكليًا وحقوقيًا أوليًا نجح، لا أن بيانات الوسوم دقيقة، أو أن التدريب بدأ، أو أن النموذج مؤهل للتطبيق. فحص فعلية فك الصور، ونسخ الأدلة، ومطابقة عدم التسرب القريب، وتنفيذ التدريب التجريبي، وقياس الجودة الجديد مراحل منفصلة.

## بعد اجتياز فحص البيانات

1. اعتماد الحقوق والوسوم بصورة مستقلة ثم تجميد بصمات التجربة وسلسلة الأصل وبيانات train/validation/test.
2. تدريب نسخ **جديدة فعلية** من Tiny الرسمي باستخدام مسارين مختبرين (رأس فقط ثم رأس + مسار دقة صغيرة)، ضمن موارد وسقف تدريب معلن، دون أي أثر لصور BDD أو نتائج النهائي المستهلك.
3. اختيار المرشح والعتبة من **التحقق فقط** بعد التأكد من كفاية الفئات وحماية الفئات التي كانت تعمل جيدًا.
4. فتح **اختبار جديد مستقل** لم يُستخدم لاختيار الأوزان وقياس mAP وRecall للكراسي والكتب والأجسام الصغيرة، ومعدلات الإنذار الكاذب ومخاطر الوصف غير الصحيح.
5. فحص ONNX وORT في CPU والمتصفح/التطبيق، ومقارنة دقة/زمن/ذاكرة فعلية على iPhone 14 Pro، والتوقف والتحول إلى Lite0/Tiny فور فشل أي شرط.
6. مراجعة مستقلة مع مستخدمين من ذوي الإعاقة البصرية للتسميات الصوتية وVoiceOver؛ لا ادعاء ملاحة آمنة أو تجنب اصطدام أو حساب درجات السلم من هذه التجربة.

**حالة هذا الفرع:** إعداد سياسة وتصنيف وفحص إدخال واختبارات؛ **لا تدريب V4 ولا وزن V4 ولا mAP جديدة ولا نشر**. البيانات المعتمدة الجديدة غير متاحة في المستودع، ونتائج iPhone الحالية لا تحتوي وسومًا مرجعية مستقلة.
